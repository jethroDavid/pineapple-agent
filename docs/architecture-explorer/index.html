At A Glance

What Pineapple Actually Is

Pineapple is not just “an agent app”. It is a small orchestration runtime with clear layers: transport adapters at the edge, a durable thread model in the middle, a serialized execution queue for ordering, and an OpenAI-agent graph for the reasoning work.

1. External systems do not talk to agents directly

Telegram, Shortcut, or future systems first become normalized `TriggerEvent` objects. That means the execution core never depends on Telegram JSON or Shortcut webhook shape.

2. Thread identity comes before model execution

Pineapple routes every trigger into a durable `Thread` first. The agent does work inside a thread, rather than creating its own ad hoc conversation identity on every request.

3. Every run is a durable execution record

Before the runtime does real work, Pineapple inserts an `AgentExecution` row with checkpointed input. That is why recovery, approval pause/resume, and operational inspection are possible.

4. Ordering is preserved by a single in-process daemon queue

Triggers, approvals, and recovery all go through the same queue. That keeps the v1 deployment simple while still preventing concurrency races inside one app process.

5. Runtime memory is split on purpose

`threads` store business thread identity, `agent_threads` store OpenAI runner session items, and `specialist_sessions` store provider-specific continuity like Codex MCP thread ids.

6. Database constraints enforce architecture rules

The schema prevents two active executions on one thread, duplicate active subject threads, and multiple pending approval decisions for one execution. Those are architecture guarantees, not just app conventions.

Bootstrap

App Startup

Startup order is one of the most important architectural details in Pineapple because the app only works if durability, queueing, runtime, and transport registration happen in the correct sequence.

What happens
  • Build runtime dependencies in `createAppRuntime()`.
  • Build the Fastify server with core and adapter routes.
  • Verify migrations were applied before serving traffic.
  • Start the daemon before initialization that needs queued work.
  • Initialize the agent runtime, then recover active runs.
  • Start listening, then reconcile adapter webhooks and bot config.
Why it matters
  • Recovery reuses the same queue semantics as live traffic.
  • External systems only point at a server that is already live.
  • The bootstrap layer stays thin and operational rather than business-heavy.

Control Flow

Execution Flows

These are the important runtime stories: startup, manual turns, webhook-triggered turns, approval pauses, and recovery after restart.

Startup

Boot order is: build runtime, verify schema, start daemon, initialize agents, recover active runs, listen, then initialize adapters.

Manual Turn

A direct HTTP run creates or loads a thread, inserts an `AgentExecution`, marks it running, executes the runtime, then completes or pauses for approval.

Trigger Flow

Adapters verify inbound data, normalize it into `TriggerEvent`, route it to a thread, then enqueue the execution in the daemon.

Approval

Approval-required tools produce runtime interruptions. Pineapple stores a pending decision plus serialized run state and resumes later.

Recovery

On restart, queued and running executions are replayed from durable checkpoint state rather than from process memory.

Concept

App Runtime

The app runtime is the assembled operating envelope of Pineapple. It is not where routing or agent decision-making happens; it is where the service decides what subsystems exist, how they are wired together, and in what order they start and stop.

What it owns
  • Dependency composition for adapters, stores, tools, runtime, and queue.
  • Lifecycle functions for initialize, close, and recovery.
  • Feature gating when OpenAI configuration is not present.
Why this is important
  • It keeps `index.ts` very small while preserving explicit startup order.
  • It makes the service operationally understandable without a DI framework.
  • It separates app composition from execution logic.

Durability

Persistence And Invariants

Pineapple stays simple by pushing correctness into a few durable records and a handful of strong constraints.

threads

Business thread identity, subject binding, metadata, title, description, `lastResponseId`, and close/reopen state.

agent_threads

OpenAI Runner session items and active agent continuity for a thread.

agent_executions

Checkpointed execution state, status, active agent, and optional serialized run state.

agent_execution_decisions

Pending approval requests with tool identity, arguments, and human-resolution state.

Execution Status

Execution State Machine

The main statuses are `queued`, `running`, `awaiting_approval`, `completed`, `failed`, and `canceled`.

queued running awaiting_approval completed failed canceled
Queued

The execution record has been inserted and accepted, but the daemon has not yet started processing it.

  • This is the first durable state after request acceptance.
  • Recovery can replay queued work on restart.

threads

Primary durable subject of the system.

  • Only one active thread may exist per subject pair.
  • Subject type and subject id must be null together or present together.

agent_executions

Checkpointed execution state and run lifecycle.

  • Only one active execution per thread.
  • `trigger_id` is unique when present.

agent_execution_decisions

Durable approval pause state.

  • Only one pending decision per execution.
  • Approved/rejected decisions must carry resolution fields.

specialist_sessions

Provider-side continuity for specialists.

  • Unique per thread and agent.
  • Stores provider thread id and JSON state.
